# Set up an Individual

Rules shared by every skill, including the Individual-write rule and the secrets rule, are in [shared rules](../start-here/references/shared-rules.md). Details are in the [procedure notes](references/procedure.md) and the [discovery prompt](assets/search-prompt.md). Never edit framework examples to hold a practitioner's local state.

1. **Ask what changed on this machine.** A new binding, a moved path, a new credential source, reading instructions to install, or a solo start. If they only want to read an existing view, follow the view's `AGENTS.md` with no setup and no tool probes, or send them to [start-here](../start-here/SKILL.md).
2. **Reuse what exists.** Use the framework checkout named by an existing binding or found in the workspace, and inspect existing bindings first. If local operations are needed and only a repository URL exists, follow the acquisition steps in the procedure notes, then read the relevant local skill. Without local file or command access, continue with an explicitly unvalidated draft and say no view was generated.
3. **Check only the tools this task needs.** Use the safe checks in the procedure notes and the versions in `framework.json`. Never run `scripts/check-tools.sh` during assisted setup or run OpenWiki to see its version. Explain a missing tool, what it enables and its package-manager route, and get consent before installing anything.
4. **Choose the roots.** Establish a visible workspace and a documents root outside the framework checkout, and keep suitable existing roots. Follow the naming defaults in the shared rules for a new personal peer. Offer to create missing folders.
5. **Bind.** Read `scripts/setup-individual.sh --help`, then bind the documents root, framework root, the checkout parent when needed, the output root and the harness. Writes are mode 600. Warn about git-backed or synced placement without blocking. Apply the Individual-write rule from the shared rules, including how `local_resources` and `path_purposes` are recorded.
6. **Record credential sources.** Keep shared interface authentication separate from private credential origin. Accept only source declarations, variable names and provider-validated locators, never a value. One binding may use several named sources, and each slot selects exactly one. Never resolve secrets during setup, print an environment, or copy configuration or locator bytes into diagnostics. See the [review checklist](assets/review-checklist.md).
7. **Install reading instructions once views exist.** Offer `--install-instruction`. It installs each repository checkout's `AGENTS.md` and the output root's `AGENTS.md` with a one-line `CLAUDE.md` import, and a shared repository gets one instruction naming all its bound views. Show each diff and get confirmation before replacing an existing instruction; `--yes` is not consent. The copies are tracked so validation can report `INSTRUCTION_STALE`.
8. **Start alone, if there is no upstream.** Run `scripts/bootstrap-solo.sh`. It creates all three tiers and their views offline. In a no-clone bundle there is no setup script; use `./context-fabric scaffold` for drafts and a checkout for bindings. Replace the scaffold examples with supported facts through the develop skills before real work. For a new Org, hand off to [develop-org](../develop-org/SKILL.md) for its reader documents.
9. **Validate and report.** Offer `--warm-up` only with network permission. Validate the bindings and report actual findings, reading exit codes as the shared rules describe. Then run the [selected-context estimate](references/procedure.md#private-maintenance-and-reading-estimates) and keep saved reports private; a passing estimate is not validation. At first setup, offer optional task candidates from scoped history with the [candidate procedure](references/procedure.md#optional-scoped-candidates), and verify any fact through the owning authoring skill.
