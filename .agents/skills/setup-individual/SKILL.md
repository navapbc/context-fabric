# Set up an Individual

1. Start with the requested task and inspect accessible context. For reading or using existing context, if a suitable generated view exists, follow its `AGENTS.md` and do the work without setup or tool probes. For authoring or maintenance, inspect existing documents and bindings before recommending the simplest suitable next step, with a reason and its limits. Do not require a clone/bundle/draft choice before useful work.
2. Reuse the framework checkout named by an existing binding or available in the workspace. If local operations are needed and only a repository URL is available, follow the acquisition steps in [procedure notes](references/procedure.md), then read the relevant local skill. Reading and template drafting need no installation; without local file or command access, continue with an explicitly unvalidated draft and state that no view was generated.
3. Check only capabilities needed for the selected operation using the safe checks in the procedure and manifest versions. Never run `scripts/check-tools.sh` during assisted setup or execute OpenWiki to inspect its version. Explain a missing tool, what it enables and its package-manager route; obtain consent before installation. Actual validator findings determine which stages ran.
4. When a new or changed binding is needed, establish a visible workspace and documents root outside the framework checkout; preserve suitable existing roots. For a new personal peer with no explicit or suitable existing destination, propose `context-fabric-personal`; use `context-fabric-personal-<profile-id>` for a second peer only from an explicit non-personal lowercase-kebab profile id, never a name or email. Stop on an unrelated collision for an explicit alternate; do not rename or number existing resources. Read `scripts/setup-individual.sh --help`, then use the shared setup, reconciliation or migration scripts for **every Individual write** except one. Bind the documents root, framework root, checkout parent when needed, output root and harness. No setup flag writes `local_resources` or `path_purposes`: they are the one sanctioned hand-edit. When the task needs them, edit the binding in the Individual document (keep mode 600) to record this machine's directories and command-line tools as `local_resources` (id, `directory` or `cli`, path, one-line purpose, optional shared system and interface) and to explain roots in `path_purposes`, then run `scripts/validate.sh --bindings <individual>` before relying on them; reruns of setup, reconciliation and migration keep them. A link to a system the bound document lacks is reported, never rewritten. Follow the procedure's lookup and explicit write-destination rules. Writes are mode 600. Warn about git-backed or synced placement without blocking.
5. Keep shared interface authentication separate from private credential origin. Accept only source declarations, variable names and provider-validated locators, never ask for or accept a secret value. One binding may use multiple named sources; each slot selects exactly one. Never resolve secrets during setup, print an environment, or copy configuration or locator bytes into diagnostics or artifacts. See the [review checklist](assets/review-checklist.md).
6. Offer `--install-instruction` after views exist. It installs each repository checkout's AGENTS.md and the output root's AGENTS.md, with a one-line CLAUDE.md import. Shared repositories get one instruction naming all bound views. Show each diff and obtain confirmation before replacing any existing instruction; do not use `--yes` as a substitute for consent. Copies are tracked for INSTRUCTION_STALE.
7. Offer the opt-in `--warm-up` only with network permission. Validate the resulting bindings and report actual findings. Exit 2 or 3 is **not validated**, with the missing stage named. For a solo start with no upstream, the separate `scripts/bootstrap-solo.sh` wrapper directly invokes the shared bootstrap unchanged; it creates all three tiers and views without network. Replace scaffold examples with supported facts through the appropriate authoring skills before using the context for real work.
   When creating a new Org, including after solo bootstrap, hand off to develop-org for its task-first README, internal one-pager and linked maintenance reference as well as supported shared facts. The agent drafts these reader documents; setup and bootstrap scripts do not generate them. Existing-view reading needs no documentation creation or setup.
8. Keep shared `identity.purpose` as task scope and facts. Personal style/preferences belong in existing harness configuration or handwritten personal root instructions; never edit generated instructions or invent Individual fields for them. At initial setup and on demand, offer optional task/context candidates and prompt estimates from explicitly scoped authorized history summaries using the [candidate procedure](references/procedure.md#optional-scoped-candidates). Verify candidate facts and useful anchors through the owning authoring skill; unavailable history does not block setup.
9. Run the [selected-context estimate](references/procedure.md#private-maintenance-and-reading-estimates), including the named view's generated instructions, applicable root/ancestor and installed instructions or aliases, Individual, required retention sidecar and any available optional prompt. Report missing selected inputs and approximation limits. Keep saved reports private; a passing estimate is not validation or proof of harness loading.

See [procedure notes](references/procedure.md) and [discovery prompt](assets/search-prompt.md). Never edit framework examples to hold a practitioner's local state.
