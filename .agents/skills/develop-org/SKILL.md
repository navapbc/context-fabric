# Develop an Org

Early in an interactive session, ask once: "Which sources should I treat as authoritative for shared systems, owners and interfaces?" This is optional. If unanswered or noninteractive, proceed with existing documents and already authorized sources, noting provenance and gaps. Do not wait for an answer before useful discovery. Rules shared by every skill are in [shared rules](../start-here/references/shared-rules.md).

1. **Choose where it lives.** Establish the documents root, outside the framework checkout, and offer to create a missing folder. For a new Org peer folder, follow the naming defaults in the shared rules. Resolve the framework through the binding or wrapper; never copy schemas or templates into this skill.
2. **Search before authoring.** Look for the systems in existing Org documents in the framework and every bound documents root. Search authorized knowledge sources with the [search prompt](assets/search-prompt.md), and treat agent memory as leads to verify. Do not claim an unavailable source was searched. Record evidence gaps; do not invent facts.
3. **Draft from the template.** Read the current Org template and its field descriptions. Run `scripts/scaffold.sh --help`, then `scripts/scaffold.sh org <id> --root <root>`. Template values are examples, not facts. A draft needs no installation and is unvalidated, not a view.
4. **Fill shared facts only from evidence.** Cover systems, interfaces and maintainers: `locators`, the applicable `cli`, `api`, `mcp` or `web` descriptors, optional `capabilities` and a declarative `probe`. Give each system and interface an optional one-line `purpose` of at most 160 characters, and an API `schema_url` an optional `spec_format`. Omit unsupported optional descriptors. Encode evidenced lack of support as `support: unsupported`, never from a failed access attempt. Group interfaces per system and present CLI, API, MCP, then web; choose by task capability and reachable authorized access, not by that order.
5. **Keep private and local things out.** Local resources, synced folders, machine paths, loopback services, installation state, preferences, secrets and personal access outcomes stay out of an Org. Setup owns private bindings, including a binding's `local_resources`. Portable CLI executable names and help tokens are shared descriptors. Specific repository records belong in a Bounded Context; an Org may name one canonical organization-level forge. Use the [review checklist](assets/review-checklist.md).
6. **Check access, read-only.** For each discovered interface, attempt a bounded read-only check when a known safe adapter or an authorized host tool exists. Follow the [access-check procedure](references/procedure.md#bounded-access-checks) and keep receipts private. Discovery, identity and content access are separate evidence, and a sign-in page is not capability success. Never execute authored command, help or probe text, sign in, request grants, mutate resources or enumerate secrets. Recording a descriptor does not authorize running it.
7. **Validate.** Run `scripts/validate.sh --help`, then validate the document, and read exit codes as the shared rules describe. Migration is different: read `scripts/migrate.sh --help`. Its pinned offline schema runner must validate the converted target before any write, and migrated locators stay unclassified until evidence supports a role.
8. **Add task entry points.** Look for folders, documents, saved queries, dashboards or repository entry points a task would start from, and put each in the tier that owns it. A maintenance receipt is provenance, not an entry point. Keep shared prose factual and scoped, and invent no fields.
9. **Generate and hand off.** Use [validate-and-generate](../validate-and-generate/SKILL.md) for views and releases. A named shared document can be validated directly; an external documents root needs an Org-only binding made through [setup-individual](../setup-individual/SKILL.md), and no Bounded Context is required. Report the read estimate from the [maintenance procedure](references/procedure.md#private-maintenance-and-reading-estimates). Have the adopter review and own the document.
10. **Draft the reader documents for a new Org workspace.** Write a short task-first README, an internal one-pager and a linked maintenance reference using the [Org documentation guide](assets/org-documentation.md). Lead with a useful task and the existing view; keep setup mechanics, version pins and estimates in the maintenance reference. These are agent-authored documents outside the framework checkout, not generated views.

## Change an existing document

Read the document and its changelog first. Edit facts you maintain. For a fact another maintainer owns, or to review a proposal against your own document, use [handle-corrections](../handle-corrections/SKILL.md). Deprecate a system or interface before retiring it in a later release, preserve identity or record renames, and never silently delete an active system. See the [maintenance procedure](references/procedure.md).
