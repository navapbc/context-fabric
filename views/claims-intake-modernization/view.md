## Source selection

- `intake-volume` — preferred: The intake counts the build pipeline publishes with each nightly run. It is derived from the same records the intake queue serves, and the delivery-tools alias stands behind it.
- `intake-volume-board-rollup` — fallback: The weekly rollup on the delivery board. It is a person's summary rather than a derived figure, so it answers when the nightly run has not completed and never contradicts it by more than a day.
- `intake-volume-spreadsheet` — rejected: A spreadsheet an analyst keeps by hand. Nobody owns it and two readers have already drawn different totals from it; recording the rejection is what stops it being proposed again next quarter.

## Limitations

- This context covers how claims reach the intake queue and not what happens to them afterwards; adjudication is a different team's boundary.
- The agency's code-quality service is deprecated and this context does not use it, so nothing here says whether an intake change would pass its gates.
- The contractor's sandbox holds synthetic records only, so a question that needs real intake volumes cannot be answered there.

## Access failures

- meridian-health-agency#public-rates-api — Called the published schedules endpoint from an agency workstation during the last release. The weekly erase cycle applies to every sandbox and has no exemption, so the request was declined. A longer-lived environment would have to be a new offering rather than an exception.
