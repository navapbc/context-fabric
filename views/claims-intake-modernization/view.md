# Claims Intake Modernization

Bounded Context view of `claims-intake-modernization`, release 1. Generated by `scripts/generate.sh`; never hand-edited.

What somebody needs in order to change how claims reach the agency's intake queue, without first asking four people which system owns which fact.

Written for: The engineers, analysts and product people working the intake stream across the agency and its delivery contractor.

## Source selection

- `intake-volume` — preferred: The intake counts the build pipeline publishes with each nightly run. It is derived from the same records the intake queue serves, and the delivery-tools alias stands behind it.
- `intake-volume-board-rollup` — fallback: The weekly rollup on the delivery board. It is a person's summary rather than a derived figure, so it answers when the nightly run has not completed and never contradicts it by more than a day.
- `intake-volume-spreadsheet` — rejected: A spreadsheet an analyst keeps by hand. Nobody owns it and two readers have already drawn different totals from it; recording the rejection is what stops it being proposed again next quarter.

## Limitations

- This context covers how claims reach the intake queue and not what happens to them afterwards; adjudication is a different team's boundary.
- The agency's code-quality service is deprecated and this context does not use it, so nothing here says whether an intake change would pass its gates.
- The contractor's sandbox holds synthetic records only, so a question that needs real intake volumes cannot be answered there.

## Access failures

- meridian-health-agency#public-rates-api — Called the published schedules endpoint from an agency workstation during the last release. The anonymous rate limit rejected the calls a workflow would need to make. A service account with its own quota would resolve it; the request sits with the rates publication alias.
- harbor-line-consulting#sandbox-cluster — Asked the contractor's platform alias for a sandbox this context could keep between weeks. The weekly erase cycle applies to every sandbox and has no exemption, so the request was declined. A longer-lived environment would have to be a new offering rather than an exception.
